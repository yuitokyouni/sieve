### `RunManifest` v1 is retained and deprecated

`schemas/RunManifest.schema.json` (`schema_version: "0.1.0"`) is unchanged and
stays. Reason: already-sealed evidence bundles embed a v1 manifest and must
keep validating; deleting it would invalidate the existing sealed record,
which is the opposite of what a provenance contract is for.

**New runs emit v2 only.** The deprecation is declared here and in the v2
schema's `description` rather than by editing the v1 file, because that file
is regenerated by `sieve schemas export` and an annotation written into it
would silently disappear on the next export — a parallel authority with a
half-life.

## 2. B5 — fail-fast and unverifiable are two different clauses

The two were previously one idea and had to be split, because they are a
run-time *measure* and an audit-time *classification* and they answer to
different people.

### 2.1 Run-time measure (fail-fast)

> A run **must abort** when a **declared** input's digest **cannot be obtained
> at the moment of consumption**.

Precisely what triggers it:

- the input is *declared* (it appears in `input_artifact_digests`), and
- at the point the run *consumes* it, no digest can be computed for it.

Precisely what does **not** trigger it: a path being unreachable. A declared
input can be unreachable and still have a digest — from a cache, a lock file,
a prior manifest — and a run that aborts on unreachability while accepting an
undigested-but-readable input has the condition exactly backwards. The
triggering condition is **digest availability at consumption**, not path
reachability.

Not covered by this clause: inputs that were never declared. Those are a
conformance-profile matter (§6), not a fail-fast matter — you cannot fail fast
on something nobody mentioned.

### 2.2 Audit-time classification (unverifiable)

> An input that was declared but for which no digest could be obtained is
> classified **`unverifiable`**, with a required `reason`, and is retained in
> the manifest.

Schema location: `input_artifact_digests[].verification` —
`status ∈ {verified, unverifiable}`, `reason` required when `unverifiable`
(if/then), and `digest` required when `verified` (if/then). The record is
**kept**, not dropped: an input that vanishes from the manifest is
indistinguishable from an input that never existed, and the second is worse
than the first.

`CanaryResult` carries the same distinction: `UNVERIFIABLE` is a verdict in
its own right, separate from `MISMATCH`. **MISMATCH is a statement about the
engine; UNVERIFIABLE is a statement about the harness.** Collapsing them is
how a broken harness gets filed as a broken model. Verified end to end: the
canary reports UNVERIFIABLE, not MISMATCH, when the input config changes
(`tests/unit/test_contract_canary.py`).

## 3. Q1 — optional in the schema, WARN in the reader, FAIL in the profile

`git_commit` and `container_digest` (schema: `code_provenance.*`) stay
**optional**. Absence is surfaced as a **WARN**, never as a schema error.

The reason is a division of labour, not leniency. A schema says what a
document *is*; a profile says what a document must be *for a given purpose*. A
CI smoke run and a publication-grade run have the same shape and different
requirements. Encoding the strictest purpose into the shape would make every
weaker run unrepresentable, and unrepresentable runs do not become stricter —
they become unrecorded.

FAIL enforcement lives in the conformance-profile layer (§6). The schema
carries the plumbing for it — `conformance_map.items[].status ∈ {SATISFIED,
WARN, FAIL, UNVERIFIABLE}` — so the profile can be written without reopening
the schema.

## 4. Q2 — where the fingerprint lives

Three decisions, one principle: **a field's type should match how it is used,
and a hash's domain should be registered rather than emergent.**

1. `dependency_lock_digest` is a **reserved key** of the `environment` map —
   named and typed in the schema for documentation, still a map entry. It is
   environment.
2. `rng_algorithm` and `rng_version` are **top-level typed fields**. The random
   stream is behaviour, not environment trivia; burying it in a
   `dict[str, str]` would make the one thing that determines the trajectory
   look like a version banner.
3. `runtime_fingerprint_domain_version` (integer) versions the **set of keys**
   that enter `environment_fingerprint_digest`.

The key list is registered in `effective_config.md` §2.1 — seven entries, five
environment keys and two top-level fields — and the consequences are enforced
by `tests/unit/test_contract_hash_domain.py`:

- adding an unregistered key to `environment` does **not** move the digest;
- changing the registered domain **does**, and is rejected unless
  `runtime_fingerprint_domain_version` is bumped;
- a top-level `rng_*` field is not satisfiable by a same-named environment
  entry, so decision 2 cannot be undone by accident.

The tests read the key list **out of the registry document**. Restating it in
code would create the second authority this whole contract exists to prevent.

## 5. B8 and the canary placement

### `seed_convention_version`

Top-level field in v2, and inside the `behavior_config_hash` domain
(`effective_config.md` §2.2). At a fixed `master_seed`, changing how children
are derived from the master changes the trajectory; a manifest recording only
`master_seed` would show two different runs as identical.

### `canary_results` lives on `RunManifest`, not in the evidence bundle

**Grounds (one line):** `EvidenceBundle.artifact_index` holds `ArtifactRef`,
which has no role field, so making a canary a "required role" there would
require modifying an existing, sealed schema — outside the approved scope.

**No payload duplication, structurally.** `CanaryResultRef` permits
`fixture_id`, `fixture_version`, `fixture_digest`, `mode`, `result_digest`,
`result_ref` and a copied `verdict` — and `additionalProperties: false`. There
is no payload-shaped property to fill, so duplication is not a rule to
remember but a thing the schema cannot express. The copied `verdict` is the
one denormalization, kept so an index can be read without dereferencing every
result; it is a copy of a value the referenced digest pins.

## 6. The conformance profile layer

Q1 defers severity to a profile. The profile itself does **not exist yet**,
and the schema deliberately does not decide it.

What the schema already provides: `conformance_map` — `profile_id`,
`profile_version`, and per item an `item_ref`, a `field_pointer` (JSON
Pointer), a `status`, and a note. That is the machine-readable half of the
resolution table in §7.

What is missing: the item list itself, and which items are FAIL in which
profile. Blocked on the same missing source as §7. Recorded as gap **G8**;
it is a freeze-checklist item and it is **not met**.
