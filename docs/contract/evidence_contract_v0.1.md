## Scope

**Contract surface** — everything below is normative and covered by the freeze:

| | |
|---|---|
| `sieve/docs/contract/` | this directory: the prose, the registry, the resolution map |
| `sieve/schemas/*.schema.json` (hand-authored) | `RunManifest.v2`, `EventLog`, `CanaryResult`, `ContHarnessInput`, `ContHarnessOutput`, `ContHarnessParameters` |
| `sieve/fixtures/canary/` | fixture format, the two fixtures, `stats_vector_spec` |

**Explicitly outside** — not covered, not frozen, may change freely:

| | why it is outside |
|---|---|
| engine code | the contract constrains what a run must *record*, not how a market is simulated. An engine inside the contract surface would make every model change a contract change. |
| PAMS adapters and reference implementations | including `fixtures/canary/_engine/*` and `tools/cont_harness_reference.py`. They demonstrate that the contract is satisfiable and are pinned by tests; they are not the contract. A second implementation must be able to disagree with them and still conform. |
| `tests/golden/fixtures/` | the parity harness against the research repository. Explicitly not reused by any canary — see `fixtures/canary/README.md`. |

**Normative declaration.** The normative artefacts are the **JSON Schema files
under `sieve/schemas/`**. `sieve/src/sieve/core/models.py` is an
implementation. Where they disagree, the schema file is right and the
implementation has a bug. `sieve schemas export` is guarded so it cannot write
over a hand-authored contract schema; a future pydantic-backed version of
these artefacts is conditional on a test asserting **export output == the
normative file** (backlog item C).

## 2. B5 — fail-fast and unverifiable are two different clauses

A run-time *measure* and an audit-time *classification*. They answer to
different people and were split for that reason.

### 2.1 Run-time measure (fail-fast)

> A run **must abort** when a **declared** input's digest **cannot be obtained
> at the moment of consumption**.

What triggers it: the input appears in `input_artifact_digests`, and at the
point the run consumes it no digest can be computed.

What does **not** trigger it: a path being unreachable. A declared input can be
unreachable and still have a digest — from a cache, a lock file, a prior
manifest — and a run that aborts on unreachability while accepting an
undigested-but-readable input has the condition exactly backwards.

Not covered: inputs never declared. That is a conformance-profile matter (§6);
you cannot fail fast on something nobody mentioned.

### 2.2 Audit-time classification (unverifiable)

> A declared input for which no digest could be obtained is classified
> **`unverifiable`**, with a required `reason`, and is **retained**.

Schema: `input_artifact_digests.<id>.verification` — `status ∈ {verified,
unverifiable}`, `reason` required when `unverifiable`, `digest` required when
`verified`, both by `if`/`then`. The record is kept because an input that
vanishes from the manifest is indistinguishable from one that never existed,
and the second is worse.

`CanaryResult` carries the same split: **MISMATCH is a statement about the
engine, UNVERIFIABLE is a statement about the harness.** Verified end to end —
changing the fixture's input config yields UNVERIFIABLE, not MISMATCH
(`tests/unit/test_contract_canary.py`).

## 3. Three hash domains, one registry

The domains and their key lists live in `effective_config.md` §2, and the
tests read the list **out of that document** rather than restating it.

| digest | domain | version field |
|---|---|---|
| `environment_fingerprint_digest` | runtime: `python`, `platform`, `numpy`, `blas`, `dependency_lock_digest`, `rng_algorithm`, `rng_version` | `runtime_fingerprint_domain_version` |
| `behavior_config_hash` | behaviour: `config`, `seed_convention_version` | `behavior_config_domain_version` |
| `effective_config_digest` | the whole resolved config | — |

Three decisions inside that, all from Q2 and the 2026-08-20 rulings:

1. `dependency_lock_digest` is a **reserved key** of the `environment` map.
2. `rng_algorithm` / `rng_version` are **top-level typed fields**, and they are
   in the **runtime domain only**. Putting the generator identity into the
   behaviour hash would make a same-engine / different-environment semantic
   canary return UNVERIFIABLE in precisely the case it exists to cover. The
   difference is still recorded and still hashed — as an environment
   difference, which is what it is.
3. `seed_convention_version` (B8) **is** in the behaviour domain: at a fixed
   `master_seed`, a changed derivation convention changes the trajectory.

Enforced properties (`tests/unit/test_contract_hash_domain.py`): adding an
unregistered key to `environment` does not move the digest; changing the
registered domain does, and is rejected unless the domain version is bumped; a
top-level `rng_*` field is not satisfiable by a same-named environment entry.

**Formula registry** — `effective_config.md` §2.3 binds each formula slot to an
`id@version` **and its effective values**. Two rows there share a `formula_id`
and differ only in effective values; without that column, `ddof = 1` and
`ddof = 0` would be the same record.

## 4. EventLog — the core field set is not ours to choose

Calendar §2.1 fixes it: **time, event type, actor role, side, price, quantity,
order/trade ID, cause ID.** Eight slots, realized by nine keys — slot 7 names
two objects with different lifetimes, so `order_id` and `trade_id` are
separate and a fill leg carries both.

`event_id` and `actor_id` are **not** core. `event_id` is a proposed
total-order key; `actor_id` is optional, because an engine with anonymous
agents is still conforming.

- **Ordering (G4).** The header declares exactly one total order key. `t` is
  permitted only when declared unique and monotone; otherwise `seq` or
  `event_id` is mandatory. `cause_id` may only reference a **preceding**
  element on that order.
- **`actor_role` (G2)** includes `exogenous_harness`. Without it a
  harness-injected shock is indistinguishable from an agent's order and no
  shock-response estimator has a treatment variable.
- **Level-I (G1)** is `l1`, profile-required for any log supplied to the Cont
  harness or to a canary. Two normative invariants: **(i) no silent change** —
  every Level-I change is attributable to some event's `l1`; **(ii) no crossed
  snapshot**. Both hold because `l1` is the state the book **settled into after
  the atomic operation**, shared by every event that operation produced. The
  quantity of a limit order that comes to rest appears in the `l1` of **its own
  submit event** — asserted, not asserted-to-be-obvious.

## 5. Canary — three parts, two preconditions

Format and the tolerance-basis vocabulary: `fixtures/canary/README.md`.
Every fixture has `precondition` / `assertion` / `tolerance`, and every
tolerance names a basis (`structural`, `numerical`, `seed_variation`,
`provisional`). A failed precondition is **UNVERIFIABLE**, never MISMATCH.

| mode | precondition |
|---|---|
| exact | three-layer hash agreement: input, effective config, environment fingerprint |
| semantic, same engine / different environment | `behavior_config_hash` agreement |
| semantic, different engines | per-field comparison of the core surface (`ext.*` excluded), pinned by digest |

`canary_results` lives on `RunManifest`, reference + digest only.
**Grounds:** `EvidenceBundle.artifact_index` holds `ArtifactRef`, which has no
role field, so a "required canary role" there would mean modifying a sealed
schema. Payload duplication is not a rule to remember: `CanaryResultRef` has
`additionalProperties: false` and no payload-shaped property, so the schema
cannot express it.

## 6. The conformance profile

**FAIL list = every §2.1 item** (ruling of 2026-08-20). There are **no WARN
items** in the contract profile. Q1 is untouched by this: the *schema* still
admits the absence — `git_commit` and `container_digest` stay optional there —
and it is the *profile*, not the schema, that makes an absence fatal. A weaker
profile may downgrade items to WARN; it may not add items.

Two further profile requirements that are not §2.1 items:

| id | requirement | origin |
|---|---|---|
| `profile.l1_inline` | a log supplied to the Cont harness or a canary declares `l1_availability: "inline"` | G1 (a) |
| `profile.terminal_snapshot` | a conforming log ends with terminal `book_level` events | G5 (i) |

And one **optional** check, deliberately not a FAIL item:

| id | check | why optional |
|---|---|---|
| `profile.reconstruction_agreement` | replay the reference book reconstruction; assert reconstructed L1 == inline `l1` | G1 (b). A disagreement diagnoses either an incomplete log or a difference in matching semantics, and telling those apart is the point of the check — not a pass/fail gate. |

**Per-run status is not in the manifest.** The manifest declares
`conformance_profile_id` and nothing more; the static item→field table is
`conformance_map.v1.json`; the verdict is produced by the profile checker and
lives beside the manifest. A manifest that judged itself would be a second
authority on conformance, and the one easiest to make agree with itself.

## 7. §2.1 → field resolution — **RESOLVED**

Machine-readable: **`conformance_map.v1.json`** — 26 items, `2.1-1a` …
`2.1-9b`, each with an RFC 6901 pointer into a `RunManifest` v2 document,
`origin` (existing / new), and `profile_status: FAIL`. Pinned by
`tests/unit/test_contract_examples.py`: the item list is exactly the calendar's,
every pointer resolves against the schema, and every item is FAIL.

Nine fields were **new** and were added to close the table:

| item | field | why it had no home |
|---|---|---|
| `2.1-1a`–`1d` | `/engine/{engine_id,engine_version,git_commit,source_digest}` | v2 had `producer` — the tool that wrote the manifest — and nothing for the engine that produced the run. Conflating them attributes a run to the harness version. |
| `2.1-5b`, `5c` | `/effective_config/resolution_sources[…]` | the resolved config was recorded; what resolved *into* it was not |
| `2.1-7a` | `/event_log_schema_version` | recorded only inside the log, so a manifest could not be checked without opening it |
| `2.1-8a`, `8b` | `/metric_suite/{suite_version,output_digest}` | absent entirely |

The seventeen remaining items map to fields that already existed.

**Correction of record.** On 2026-08-21 the core field set was *inferred* from
